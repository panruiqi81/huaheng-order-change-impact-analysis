## 原型（阶段 05–06）

纯标准库 Python，无第三方依赖。读取四系统脱敏快照，核对排产版本、产能缺口与质量冻结，输出“已确认事项 + 待审批事项（待谁批）”。

```bash
cd prototype
python3 -m oc_checker --snapshot data/base --order O-202610-001 --out out/   # 运行一次核对
python3 -m unittest discover -s tests                                        # 7 项单元测试
python3 tools/run_eval.py                                                    # 17 个评估用例
```

基准场景（`data/base/`）的结论为**需关注**：ERP 存在待批准的 V3，MES 排产 P17 与已批准的 V2 一致，按 V3 测算缺口 100 件，列出 3 项待审批。完整报告见 [`prototype/eval/base-report.md`](prototype/eval/base-report.md)，评估结果见 [`prototype/eval/results.md`](prototype/eval/results.md)（17 / 17 通过）。

> 仓库内数据均为按访谈事实构造的合成数据，不含真实客户或业务记录。

## 关键结论

**阶段 01–02：问题在哪**

1. **问题成立**：版本不同步（ERP V3 vs MES P17/V2）由销售与生产计划两个角色**独立陈述**，非单一视角。
2. **口径必须先锁定**：86% 交付率存在“按订单行”与“按客户订单”两套口径，不可直接比较，试点验收前须书面确认。
3. **四来源未闭合**：Buyer 与 Operator 有证据，**Brief（书面范围）与 Industry（行业依据）缺失**，按规则保留为待补，不以推断替代。
4. **硬约束**：质量冻结批次 B-17 不因交期压力绕过放行；返工完成 ≠ 检验通过；一次错误放行即暂停试点场景。

**阶段 03–09：做成什么样、值不值**

5. **工具只做三件事**：核对版本、测算缺口、检查冻结。会签、加班审批、质量放行只能由人做；质量放行与对外承诺两处不可逆，工具不出结论性动作。
6. **ROI 按工时口径不成立**：六个输入均无实测值；纯协调工时口径下即使乐观情景也需 43 个月回本，多数情景不回本。价值更可能来自避免版本冲突损失，但单次损失无数据——试点期必须同时采集业务量、每单节省时间、冲突损失三个量。
7. **原型在合成数据上达标**：17 个用例的结论与事先写定的预期全部一致，10 条红线均有用例或测试覆盖且未被突破；未覆盖真实数据、自然语言说明与一线使用。
8. **上线前有 6 项缺口要业务方关闭**，首要的是“批准版本由谁签发、以哪个系统为准”。

**报价包：多少钱、值不值**

9. **62 人天，首年 18.8 万元**：一次性实施费 159,978 元 + 年服务费 28,181 元。模型费可忽略（年约 3.7 元），成本大头在系统集成与规则工程。
10. **首年不回本，第二年起每年净赚约 11.6 万元**：首年 ROI −23.4%，第 16–17 个月回本，三年 ROI 76.9%。年收益 14.4 万元里只有 2.4 万元来自工时节省，其余 12 万元取决于“年避免 12 次版本冲突、单次 2 万元、降低 50%”这一项无数据支撑的假设；只算工时则不回本（需月 311 单才回本）。详见 [`pricing/README.md`](pricing/README.md) 与 [`pricing/报价包.md`](pricing/报价包.md)。

## 边界（明确不做）

- ❌ 不写入生产系统（ERP / MES / WMS / QMS 仅只读快照）
- ❌ 不自动向客户发送交期承诺
- ❌ 不自动解除质量冻结
- ❌ 模型故障时不得以缓存结果冒充本次核对成功，必须转人工

## 人工关卡（只能人做）

会签（生产计划 + 销售）· 加班审批（工厂经理 + 人事）· 质量放行（质量负责人）—— 工具仅提示“待谁批”，不得替代审批。
