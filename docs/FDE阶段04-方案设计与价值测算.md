## 任务 1 方案设计与备选比较 · 已完成

**约束条件**（来自阶段 03）：三件事只能由人做；两处不可逆点（质量放行、对外承诺）工具不得出结论性动作；四系统只提供脱敏 CSV 或只读快照（f30）；输入不完整时转人工（f32）。

| 备选 | 做法 | 满足约束？ | 结论 |
|---|---|---|---|
| A 全自动排产调整 | 读取变更单后直接改写 MES 排产 | ❌ 需要写接口（f30、f35）；替代了批准的生产计划（f25）；周明远已表示证据不足时接受只读试点（f03） | 排除，保留编号 |
| B 只读核对助手（**选定**） | 读取四系统快照 → 核对版本、产能、质量 → 输出“已确认事项 + 待审批事项”，全程只读 | ✅ 不写入、不替代审批、不对外发送 | 进入构建 |
| C 变更提醒看板 | 只做“有新变更单”的提醒，不做核对 | ✅ 但不回答“哪一版算数”“缺口多少”（f20、f21） | 作为 B 的后续扩展 |

**B 方案的处理流程**：

```
快照导入 → 校验（缺文件/脏数据 → 转人工）
        → 版本核对：ERP 批准版本 vs MES 排产版本
        → 质量检查：订单占用批次的冻结 / 返工 / 放行记录
        → 产能测算：已确认产能 + 可用库存，按版本分别算缺口（待批加班单列）
        → 输出：已确认事项 / 待审批事项（待谁批）/ 审计信息
```

**设计要点**：

- “已批准”的定义取 ERP 中状态为已签发（released）的最高版本；会签完成但未签发不算批准（f14、f23）。**该定义是待会签双方书面确认的假设**（阶段 03 缺口 1）。
- 缺口按 ERP 中每个版本分别测算，未批准版本只作情景，不构成产能承诺（f21、f22）。
- 质量状态以 QMS 带版本和时间的记录为准，QMS 与 WMS 不一致时按同步延迟处理并提示（f41）。
- 缺记录不等于零：订单在 WMS 没有库存行时按 0 测算但转人工确认。

**交付**：方案 B 的流程与规则定义，作为阶段 05 的构建依据。

## 任务 2 报价与 ROI 测算 · 已完成

**先说结论**：按“节省协调工时”口径，即使乐观情景也需要 43 个月回本，多数情景不回本；本项目的价值更可能来自避免版本冲突造成的损失，但那部分目前没有数据。**因此本任务的产出是一个可复算的测算模型和待确认输入清单，而不是一个 ROI 数字。**

**六个输入**（阶段 01 已点名，现全部为待确认的假设值）：

| 输入 | 符号 | 假设值 | 依据与状态 |
|---|---|---|---|
| 一次性报价 | P | 30,000 元 | 假设：4 周试点 + 规则开发，内部自研无外部采购价 |
| 月运行费 | C | 500 元 / 月 | 假设：快照导出与复核工时，未取数 |
| 月业务量 | N | 20 / 40 / 60 单 | 未知：仅有“客服日均约 45 条咨询”（f50），未按订单号归集 |
| 每单节省分钟 | M | 10 / 20 / 30 分钟 | 未知：仅有“同单至少追问两轮”（f50），单轮耗时无样本 |
| 时薪 | W | 80 元 / 小时 | 假设：未取工资数据 |
| 兑现比例 | R | 0.5 | 假设：节省的工时只有一部分能转为有效产出 |

**工时口径**：月节省 S = N × M ÷ 60 × W × R；回本月数 = P ÷ (S − C)，S ≤ C 时不回本。

| 月节省 S（元） | M = 10 分钟 | M = 20 分钟 | M = 30 分钟 |
|---|---|---|---|
| N = 20 单 | 133（不回本） | 267（不回本） | 400（不回本） |
| N = 40 单 | 267（不回本） | 533（900 个月） | 800（100 个月） |
| N = 60 单 | 400（不回本） | 800（100 个月） | 1,200（43 个月） |

要在 12 个月内回本（月净收益需 3,000 元），N = 40 单时每单需节省约 112.5 分钟——远高于“少追问一轮”能解释的量级。

**避免损失口径**（待数据验证的替代模型）：若每月避免 k 次版本冲突事件、单次损失为 L，则月净收益 = k × L − C。12 个月回本所需：k = 1 时 L ≥ 3,000 元，k = 2 时 L ≥ 1,500 元。**L 需向王建国、陈思雨索取返工工时、插单调整与客户补偿记录后才能填**，现阶段不填。

**对试点的影响**：

1. 试点期内必须同时采集 N、M、L 三个量，否则试点结束时仍然算不出 ROI——这比工具本身的功能更重要。
2. 若业务方只认工时口径，建议缩小 P（例如复用现有快照导出、不做界面）或放弃立项，而不是调高假设值让数字好看。
3. 协调操作时间与等待审批时间须拆开记录（f04），否则耗时下降分不清是流程改善还是审批被绕过。

## 任务 3 技术架构与安全边界 · 已完成

**架构**（纯标准库 Python，无外部依赖，便于在内网离线运行）：

```
prototype/
├── data/base/            五张脱敏快照（合成数据）
├── oc_checker/
│   ├── models.py         快照加载与校验（脏数据记错，不猜测）
│   ├── rules.py          核对规则（版本 / 产能 / 质量 / 待确认清单）
│   ├── audit.py          任务编号与哈希绑定
│   └── render.py         报告渲染（Markdown + JSON）
├── eval/                 评估集与结果
└── tests/                单元测试
```

**数据契约**（字段口径待沈悦确认）：

| 快照 | 关键字段 | 说明 |
|---|---|---|
| ERP 变更单 | 订单号、版本、数量、交期、状态、提出时间、录入时间、会签与质量审批标记、签发人与时间 | 状态取值：proposed / countersigned / released |
| MES 排产 | 排产号、订单号、排产版本、数量、产线、更新时间 | 一单可能多条排产 |
| 产能 | 产线、时间窗、已确认产能、待批加班 | 待批加班不进入合计 |
| WMS 库存 | 订单号、SKU、批次、可用量、WMS 冻结状态、记录时间 | 缺行不等于零库存 |
| QMS 质量记录 | 批次、冻结状态、记录版本、生效时间、记录时间、签发人 | 同批次多条取最新版本 |

**安全与审计边界**：

- **只读**：程序对快照目录只做读取；测试断言运行前后快照哈希不变且目录内不产生新文件。
- **可回溯**：任务编号 = 日期 + SHA-256(规则版本 + 订单号 + 各输入文件哈希) 前 8 位；`manifest.json` 再记录各输出文件哈希，形成“输入 → 任务编号 → 输出”闭环（f31）。
- **不冒充**：程序没有任何缓存或历史结果；输入不合法时不输出部分结论（f32）。
- **数据最小化**：快照为脱敏数据，不含客户名称、价格与人员联系方式；签发人仅保留姓名用于判断放行记录是否有效。
- **明确不具备的能力**：不写回任何系统、不发送消息、不生成放行批准、不裁定版本归属（f13、f30、f45）。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| “已批准”字段定义与实际会签规则不符 | 作为阶段 03 缺口 1，由会签双方书面确认后再上线；规则版本号随定义变更递增 |
| 字段命名与版本口径在四系统间不一致（f34） | 数据契约评审时逐字段比对，差异记入待确认清单 |
| 规则被误当作审批依据 | 报告首页声明“不构成对外交期承诺”；待审批事项只写“待谁批” |

**交付下一阶段**：方案 B 流程、数据契约、审计设计，作为阶段 05 构建与阶段 06 评估的依据。
