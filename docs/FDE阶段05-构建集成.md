## 任务 1 数据契约与快照接入 · 已完成

**要解决的问题**：四系统只提供脱敏 CSV 或只读快照（f30），不同系统的记录需按订单、批次和版本关联（f34）。

**事实层**：ERP 出现 V3 而 MES 排产仍为 V2（f20）；可用产能 900 + 库存 200（f21）；QMS 与 WMS 冻结状态曾有同步延迟（f41）；返工批次需重新检验（f42）。

**合成基准快照**（`prototype/data/base/`，按案例事实构造）：

| 快照 | 内容 | 对应事实 |
|---|---|---|
| `erp_change_orders.csv` | V2：1000 件、已批准；V3：1200 件、交期提前、已提出未会签；V3 的录入时间比提出时间晚 35 分钟 | f10、f12、f14 |
| `mes_schedule.csv` | 排产 P17 按 V2 排 1000 件，产线 L1 | f20 |
| `capacity.csv` | 交期窗口内已确认产能 900 件，待批加班 150 件 | f21、f22 |
| `wms_inventory.csv` | 订单占用批次 B-16，可用 200 件 | f21 |
| `qms_holds.csv` | B-16 已放行（有签发人）；B-17 处于冻结（未签发放行） | f40、f42 |

**接入规则**：

- 加载时逐行校验必填字段、整数、枚举取值；任何一行不合法都记录文件名与行号，整次核对转人工，不跳过脏行继续算。
- “签发人、签发时间”允许为空——未签发的版本本来就没有；放行记录缺签发人由规则层判为硬约束中止。
- 同一批次多条质量记录时取记录版本与生效时间最新的一条（f41）。

**待确认**：真实快照的字段名、版本口径与留存周期（沈悦，阶段 03 缺口 6）。合成快照的字段是按访谈语义设计的，接入真实数据前需做一次字段盘点。

## 任务 2 核心核对规则实现 · 已完成

**实现位置**：`prototype/oc_checker/rules.py`（约 250 行）

| 规则 | 逻辑 | 结论级别 | 事实依据 |
|---|---|---|---|
| R1 版本一致性 | 找出 ERP 中已签发的最高版本作为批准版本；与每条 MES 排产版本比较：无批准版本 / 落后 / 超前 / 一致；存在未批准的新版本时单独提示 | 冲突 / 需关注 | f11、f14、f20、f23、f25 |
| R2 质量冻结 | 订单占用批次若冻结、返工未检、放行无签发人 → 不计入可用量；无质量记录 → 转人工；QMS 与 WMS 状态不一致 → 提示同步延迟 | **硬约束中止** / 转人工 / 需关注 | f40、f41、f42、f45 |
| R3 产能缺口 | 已确认产能 + 可用库存，对 ERP 每个版本分别测算缺口；待批加班只单列不进入合计；无库存行 → 按 0 测算但转人工 | 需关注 / 转人工 | f21、f22 |
| R4 待确认清单 | 由前三类发现生成，每项写明事项、答复人、依据；会签 → 生产计划 + 销售，加班 → 工厂经理 + 人事，放行 → 质量负责人，缺口处置 → 销售 | — | f22、f23、f43、f54 |
| R5 结论合成 | 取所有发现中最严重的一级作为总体结论；输入不合法时不执行规则，直接转人工 | 五级 | f32 |

**结论级别**：一致（OK）＜ 需关注（ATTENTION）＜ 冲突（CONFLICT）＜ 硬约束中止（HARD_STOP）；转人工（MANUAL_REVIEW）表示本次核对未完成。

**基准场景的实际输出**（O-202610-001，完整报告见 [`eval/base-report.md`](../prototype/eval/base-report.md)）：

- 总体结论：**需关注**
- 已确认：ERP 当前批准版本 V2；排产 P17 按 V2 执行，与批准版本一致
- 版本：ERP 存在待批准的新版本 V3（1200 件，尚未会签）
- 产能：按 V3 测算 900 + 200 = 1100 件，缺口 100 件；待批加班 150 件未计入
- 待审批：P1 变更单 V3 的会签与签发（生产计划 + 销售）｜P2 缺口 100 件的处置（销售）｜P3 加班能否计入产能（工厂经理 + 人事）

这个输出与访谈中各角色的陈述一致：工具把“卡在哪、等谁”列了出来，没有替任何人做决定。

## 任务 3 审计留痕与人工关卡集成 · 已完成

**事实层**：模型与规则版本、输入快照、输出须绑定同一任务编号（f31）；故障时转人工，不得以缓存冒充核对成功（f32）。

**实现**（`prototype/oc_checker/audit.py`）：

- 任务编号 `HH-<日期>-<摘要前 8 位>`，摘要 = SHA-256(规则版本 + 订单号 + 各输入文件哈希)。输入变一个字节，任务编号就变。
- 每份报告（Markdown 与 JSON）都带任务编号；`manifest.json` 记录全部输入与输出文件的 SHA-256。
- 程序内不存在缓存、历史结果或默认值兜底；输入不合法时报告只写转人工原因和输入问题明细。

**人工关卡的集成方式**：不集成。会签、加班审批、质量放行在工具之外完成，工具只在“待审批事项”里写明“待谁批”，不提供任何 approve / release 动作，也没有写入接口。

**运行方式**：

```bash
cd prototype
python3 -m unittest discover -s tests          # 单元测试
python3 tools/run_eval.py                      # 跑评估集，写 eval/results.md
python3 -m oc_checker --snapshot data/base --order O-202610-001 --out out/
```

**交付下一阶段**：可运行的原型 + 合成基准快照 + 审计清单，作为阶段 06 评估对象。
